## Slide 4 — 評価モデルとアーキテクチャ（60 秒）

### スライド文言

**重み付き線形スコア Jᵢ**（`model.py` · 小さいほど良い）

```text
Jᵢ = w₁·d + w₂·(100−C)/100 + w₃·(WBGT/40)    ← 各項 [0,1]
涼み場順位 = 0.6×(徒歩距離/800m) + 0.4×Jᵢ
```

**パイプライン**

```text
pipeline --sample → features.parquet → GeoJSON → Leaflet（HTML/JS）
```

- Python: サンプル気象・POI 32 点・格子 400 点を処理
- ブラウザ: 重み変更を **O(N) で即時再計算**（`app.js`）
- 公開: GitHub Pages（push 時に pipeline 自動実行）

**重みプリセット**: balanced / elderly / commuter / heat_alert

### 台本

「中核は **3 つの条件を 0 から 1 に直して、重み w₁,w₂,w₃ で足す** シンプルなスコア Jᵢ です。機械学習は使いません。  
涼み場 Top 3 は、Jᵢ に加えて **距離 60%・Jᵢ 40%** の合成スコアで並べます。  
データは Python の `pipeline --sample` で GeoJSON に出力し、ブラウザはサーバーなしで地図表示します。」

# 質疑応答 — 防衛カード（実装ベース）

### Q1. データパイプラインとは？

**A.** `python -m heat_town.cli pipeline --sample` 一発で、サンプル気象 CSV・POI GeoJSON・格子 400 点を生成し、`features.parquet` と `scores.geojson` / `rest_spots.geojson` を `mvp/public/data/` に出力する一連の処理です（`cli.py` → `samples.py` → `preprocess.py` → `export.py`）。

---

### Q2. なぜ `pipeline --sample` か？

**A.** seed=42 の **決定論的サンプル** で、誰が clone しても同じ GeoJSON が再現できます。GitHub Pages のビルドも同コマンドでデータを生成します（生成物は Git 管理外）。

---

### Q3. POI（公園・樹・ビル影）の根拠は？

**A.** `samples.py` が **32 点**（公園 6・街路樹 18・ビル影 8）を GeoJSON 形式で生成しています。涼み場の快適度 C は **kind 別のルール**（公園 92 / 樹 82 / ビル影 76 ベース + 風、`rest_finder.py`）です。

---

### Q4. 快適度 C とは？

**A.** 0〜100 のスコアで、高いほど快適です。

- **格子 400 点**（`preprocess.py`）: 最寄り POI までの距離と風速から `C = 0.8·c_green + 0.2·c_wind`
- **涼み場 POI**（`rest_finder.py`）: 種別（公園/樹/ビル影）+ 風

Jᵢ では **(100−C)/100** を [0,1] の「不快度」として使います。

---

### Q5. Jᵢ とは？ 式は？

**A.** 地点 i の総合スコア。**低いほど望ましい** 休憩候補です。

```text
Jᵢ = w₁·d + w₂·(100−C)/100 + w₃·(WBGT/40)
```

- **d**: [0,1] — 格子は origin から 1500m 正規化、涼み場は徒歩 800m 正規化
- **WBGT**: 気温・湿度からの推定式（`preprocess.py`）、式中は `/40` で [0,1] 化

実装: `src/heat_town/model.py` の `compute_ji`

---

### Q6. なぜ機械学習を使わない？

**A.** popup で **距離・不快・暑さの寄与** を分けて見せるためです。`compute_contributions` が 3 項を返し、分析モードのバー表示に使っています。

---

### Q7. 重み w₁,w₂,w₃ の根拠は？

**A.** `config/weights.yaml` の **ペルソナ別事前設定**（balanced / elderly / commuter / heat_alert）。スライダー変更時は `normalize_weights` で合計 1 に正規化します。データから自動推定はしていません。

---

### Q8. 単位の違う量を足すのは大丈夫？

**A.** 足す前に **すべて [0,1] に正規化** しています（`normalize_ji_terms`）。距離 d、不快度 (100−C)/100、WBGT/40 です。そのうえで w を掛けて足します。

---

### Q9. Top 3 の並び方は？ Jᵢ だけではない？

**A.** 涼み場は **合成スコア** で並べます（`rest_finder.py`）。

```text
score = 0.6 × (徒歩距離/800m) + 0.4 × Jᵢ
```

例: ビル影 5（160m, Jᵢ=0.34）が 1 位、街路樹 11（434m, C 更高だが Jᵢ=0.42）が 3 位 — **近さを 60% 反映** した結果です。

---

### Q10. WBGT とは？

**A.** 暑さ指数（℃）。`estimate_wbgt` で気温・湿度から推定し、バナーと Jᵢ の第 3 項に使います。デモデータではエリア共通値（例: 36.5℃ 前後）です。

---

### Q11. 400 点格子の意味は？

**A.** 有明 2km 四方を **100m 間隔** で置いた **400 点** の評価用格子です。分析モードで Jᵢ を色分け表示し、重みスライダーで O(N) 再計算します（`app.js`）。

---

### Q12. すずみばとの違いは？

**A.** 現場 UX は Top 3 + ナビで似ています。heat-town は **Jᵢ の式と寄与** で「なぜその順位か」を説明できる PoC です。

---

### Q13. エリア外から開いたら？

**A.** データは有明 2km・サービス半径 1500m です。GPS がエリア外、または `?demo=1` のときは **有明に補正** し、Maps も有明起点です（`resolve_user_location`）。

---

### Q14. Python と JavaScript で式が二つある？

**A.** 初回表示は GeoJSON、**重みスライダー変更時** はブラウザで即時再計算するため、同じ式を `model.py` と `app.js` に置いています。`tests/` で Python 側を検証しています。

---

### Q15. 因果関係・安全を保証できる？

**A.** **できません**。Jᵢ は **相対的な優先順位** のための指標です。「よりマシな休憩候補」を示す PoC です。

---

### Q16. GitHub Pages の仕組みは？

**A.** `main` へ push すると `.github/workflows/deploy-pages.yml` が `pipeline --sample` を実行し、`mvp/public/` を静的公開します。URL: https://kanshovector.github.io/Heat-Town/
