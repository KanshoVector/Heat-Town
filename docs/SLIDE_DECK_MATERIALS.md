## Slide 1 — 課題（45 秒）

### スライドに載せる文言

**猛暑の外勤 — 「どこへ逃げればいいか」が分からない**

- 配達・営業・イベントスタッフは、日差しの下で **10 秒以内** に判断したい
- 気温マップや研究データだけでは **「次にどこへ歩けばいいか」** が分からない
- 熱中症は **場所選び** の問題でもある

### 原稿

「みなさん、真夏に外で働いた経験はありますか。暑いのは分かる。でも **次にどこへ行けば日陰や公園で休めるか** が、スマホ一つではすぐ分からない。heat-town は、この **"逃げ場所が分からない"** 問題を、ワンタップで解決しようとしたプロジェクトです。」

---

## Slide 2 — 解決策 heat-town（45 秒）

### スライドに載せる文言

**heat-town = データを見せるのではなく、行動させる**

| 従来の PoC | heat-town |
|-----------|-----------|
| 400 点の色付き地図 | **近くの涼み場 Top 3** |
| 研究者向けスライダー | **Google Maps 徒歩ナビ** |
| 「暑い地点」が分かる | **「ここへ行け」** が分かる |

### 原稿

「私たちの答えは **すずみば** のような体験です。地図上の点の羅列ではなく、**近くの涼しい場所 3 つ** を出して、**そのままナビを起動** します。裏側ではデータ分析もしていますが、**表から見えるのは "行動"** です。」

## Slide 3 — 実装アーキテクチャ（50 秒）

### スライドに載せる文言

```
Open Data → Python CLI → GeoJSON → 軽量 HTML/JS 地図
```

- **Python**: 気象・公園・樹のデータを処理 → 涼み場スコアを計算
- **100m おき約 400 点**: 分析用。100m ごとに区切って **素早く計算**（O(N)）
- **ブラウザ**: 重みを変えると **その場で再計算**（サーバー不要）
- **Vercel**: デプロイ時にデータを自動生成（Git に大きなファイルを載せない）

### 原稿

「技術的にはシンプルです。Python でデータを作り、GeoJSON という地図用ファイルに出力。ブラウザは HTML と JavaScript だけ。**重いサーバーも AI も使いません**。100m おきに地点を置いているのは、**速く全体を見るため** の PoC 用の区切りです。」

## Slide 5 — 正直な限界（60 秒）★ 超重要

### スライドに載せる文言

**言い訳なし — できていないこと**

| 項目 | 現状 |
|------|------|
| 建物の **リアルタイム日陰** | ❌ 未実装（公園・樹・ビル影の **位置** で代用） |
| **太陽の角度** による時間変化 | ❌ 未実装（1 時刻の静的データ） |
| **リアルタイム WBGT** | ❌ 未接続（推定式 + サンプル気象） |
| **100m / 400 点メッシュ** | PoC 固定。将来はデータに合わせて間隔を変えたい |
| **対象エリア** | 有明 2km のみ（他地域はデモ補正） |

### 原稿

「ここが一番大事です。**言い訳はしません**。建物の影を光線で計算するような **本格的な日陰シミュレーションは入れていません**。今は OpenStreetMap 上の **公園や街路樹の位置** で '涼しそうな場所' を推定しています。暑さ指数も **リアルタイム API ではなく、サンプルデータ** です。100m おき 400 点は **PoC 用の決め打ち** で、本番ではもっと賢い区切り方を検討します。」

## 質疑応答 — 防衛カード

### Q1. 「日陰の精度は？ 本当に涼しいの？」

**A.** 正直に、**建物の影のリアルタイム計算はしていません**。公園・街路樹・ビル付近を OpenStreetMap から取り、**「その近くなら日陰・緑がある可能性が高い」** というプロキシで快適度を推定しています。絶対的な温度保証ではなく、**近くで休める候補を優先順位づけ** するツールです。

### Q2. 「重み付け（w₁, w₂, w₃）の根拠は？」

**A.** **ペルソナ別の事前設定** です。一般・高齢者・通勤・猛暑日で「距離」「不快度」「暑さ」の importance を変えています。PCA 等の自動決定は **していません**（説明可能性を優先）。notebook で感度分析し、**重みを変えると順位がどう変わるか** を示せます。

### Q3. 「400 点格子の意味は？ ナイキスト采样とか？」

**A.** **2km 四方を 100m おきに置いた PoC 用の区切り** です。理論的な最小サンプル数の主張は **していません**。速さ（O(N)）とブラウザで即再計算できることの **バランス** です。

### Q4. 「データは本物？ サンプルでは？」

**A.** 現在は **`pipeline --sample`** で決定論的サンプルを生成しています。Open-Meteo / OSM 相当の形式ですが、**実 API 取得は Phase 2**。PBL では再現性とライセンスを優先しました。

### Q5. 「すずみばと何が違う？」

**A.** すずみばは **施設 DB + ナビ** が本番品質。heat-town は **なぜそこが選ばれたか**（距離・快適度・暑さの式と寄与）を **説明できる** 研究 PoC です。現場 UX はすずみば型、分析は行政・PBL 向け、の **2 層** です。

### Q6. 「越谷から開いたら動くの？」

**A.** サービスデータは **有明 2km** のみです。GPS がエリア外の場合、**自動で有明に補正** し、Google Maps も **有明起点** のルートを開きます。発表は **`?demo=1`** 推奨です。

### Q7. 「機械学習で精度を上げないの？」

**A.** **Explainability First** です。線形モデルなら「距離が何点・暑さが何点」と **内訳を見せられる**。ブラックボックスより、行政・市民への **説明** を優先しました。

### Q8. 「因果関係を言える？ 本当に安全？」

**A.** **言えません**。Jᵢ は **優先順位づけの指標** であり、因果の主張ではありません。相対的に **"よりマシな休憩候補"** を示す PoC です。
